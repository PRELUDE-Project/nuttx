# taskディレクトリ全C原典の終了経路棚卸し

固定be86b519のGitHub contents/sched/taskから列挙し、26個のCファイルを全件取得して本文を確認した。sources.jsonは各blobとrecover/exithook/release_tcb参照位置。これはsched/task配下の範囲であり、sched全体・arch・driversの網羅ではない。

直接のnxtask_recover呼出はtask_exithook.c:432とtask_restart.c:105。通常exit.c:97はexithookを呼ぶ。外部終了task_terminate.c:179もexithookの後にTCBをreleaseする。

注意すべき原典差: task_terminate.cの説明にはtask_exitからterminateを通るような記述があるが、現在のtask_exit.c実体は147行でnxsched_release_tcbを直接呼ぶ。従って説明コメントだけを根拠に全経路recover済みとは判断できない。通常_exit側のexithook呼出が先行する実経路を維持することが必要で、archからのnxtask_exit呼出網羅は未完。

追加確認: execve成功は_exit(0)へ進み、別のTCB置換cleanup APIを使わない。nxtask_uninitはinactive listから除去し直接releaseするが、原典契約はtask_init後のactivate失敗回復。forkのsetup失敗/abortも子TCBを直接releaseし、start_forkのactivateより前の経路として実装される。これらで実行中SD所有者を解放してよいとは解釈しない。実呼出元まで含めた契約遵守は未証明。

この棚卸しから新たに無条件のrecover hookをrelease_tcbへ挿入しない。初期化未完TCB・異なる解放文脈へ副作用を広げるため。単純な二重通知でもslot解除後なら無害、というhost結果だけでは実OSへ追加する根拠にならない。

コード変更・実OS実行・対象build・実機操作はない。26ファイルの静的原典確認と既存通知挿入位置の限界を具体化した。物理IDMA停止・電源HOLD・正式H753設定の未確認は継続。

# Numeric PID versus task lifetime

PR #1 current HEAD 431fd0ea0f2a4f9a178fa46d9a53c46235a2433f verified. Source records in sources.json were read at that commit and Git-blob verified: sched/task/task_setup.c and sched/sched/sched_releasetcb.c. nxtask_assign_pid chooses a numeric next_pid from g_lastpid, returns to 1 for nonpositive candidates, and uses an available PID hash slot. nxsched_releasepid clears the slot; nxsched_release_tcb invokes it for an assigned PID. This is not an immutable task-incarnation identity. We did not execute PID wrap, task deletion or the full allocator.

A new actual-driver host test distinguishes two conditions using an explicitly retained lease key and changing only the mocked current task ID. A different ID is rejected. After timeout has quarantined the lease, returning to the old numeric ID plus delayed DATAEND still returns ETIMEDOUT, preserves output and cannot reclaim. Without timeout/sealing, apparent successful completion and the same retained key/numeric ID pass finish and copy. Both modeled branches pass UBSan; the second intentionally demonstrates a limitation, not a safety pass. It assumes a saved valid key remains available: it does not demonstrate arbitrary new tasks acquiring the key or an actual deployed exploit/fault.

Generation protects different lease acquisitions, but does not independently represent an OS task incarnation during one lease. A TCB pointer substitution alone is not a proven remedy because allocation addresses can be reused and holding a raw TCB pointer does not pin lifetime. Looking up a live PID before operation similarly cannot distinguish a later incarnation. No such speculative product change was made.

Safe application condition remains a trusted diagnostic owner that is not externally deleted while the lease is active. A robust broader product design requires a persistent dedicated operation owner, immutable request ownership/token, defined task exit/cancellation notification and a verified completion/join boundary; after uncertain hardware termination the static arena must remain quarantined. New task identity support or cleanup changes must be validated against real OS paths rather than host IDs. Hardware stop and task lifetime are separate obligations.

This work adds neither worker execution nor a multiple-worker safety claim. Existing queue/coalescing findings remain unchanged. Formal H753 config, target ARM build, physical stop and power HOLD are unresolved. No installation, GitHub mutation, task control or physical operation was performed.

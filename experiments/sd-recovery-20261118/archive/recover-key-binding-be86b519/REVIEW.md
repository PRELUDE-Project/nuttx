# 通知先と lease key の結び付け

対象 PR #1 は照合時 be86b5194ed8f88009c3f867bda71420a5b9d161 のまま。製品変更・公開・対象ビルド・実機操作なし。

前回独立レビューで指摘された、通知callbackがmutable global targetとgenerationのみを参照する試案の弱点を修正した。新しい隔離試案はstatic bindingに変更不能なdevice pointerを持ち、登録時にinstance/owner/generationを保存する。callbackはnoticeを含むbindingからdeviceを取得し、製品の実 scr_lease_matchesで完全keyを照合してからscr_sealする。callbackはtest用global targetを参照しない。登録失敗なら既存keyを変更しない。

run.pyで実recover＋実seal＋固定wd_cancelを接続したhostコードを生成しUBSan成功。正常通知ではECANCELED隔離、遅延IRQ後の出力不変、IDMAEN保持を確認。owner/generation/instanceを人工的に不一致へした3条件では、旧通知が現leaseを隔離しないことを確認。重複登録はEBUSYで保存keyを変えず、owner TCBのモデルidとkey不一致はESTALEで未登録のまま。

これらは実OSのPID再利用や複数controllerを実行した結果ではない。現在の試験targetは固定の単一controller。mismatchは契約境界を検査する故障注入であり、実物でleaseを書き換えて再利用してよいことを意味しない。TCB idもhostモデルであり実TCBのincarnation証明ではない。

未完条件は残る。実driver claimと通知登録を同じcritical区間へ統合する処理、登録失敗時の隔離、正常HANDOFF/RETIRED時の条件付き解除、全recover呼出と実割込排他、正式configとbuild guard、実OS終了・restart試験が必要。現在はclaim後にテストが登録するため、その間に実タスク削除が起きないという保証を追加したものではない。汎用通知APIの再入assert依存も未解決。製品の所有者終了問題を修正済みとは扱わない。

## 独立レビュー結果
別担当がソースを読み、既存binaryの4状態を再実行してPASS。単CPU・同criticalを前提にcallback内のglobal target依存、完全key照合、登録失敗時key保持は改善した。一方、上記のclaim〜登録の非原子区間とHANDOFF解除の原子性は必須未達。

追加指摘として、scr_sealは保存binding.keyではなくdeviceのscrkeyを使用する。両keyの一致不変条件を実製品への接続時に検査する必要がある。旧通知不一致でACTIVEが残る試験結果は、誤った所有者へ隔離を適用しないことだけを示し、そのACTIVE要求の終了安全性を保証しない。実TCB取得・停止順序とPID再利用も未証明のまま。
